# ABORT Review — Round 6, cut v0.5.1

Candidate: `release/v0.5.1` off `develop`, 6 commits ahead of `main` at v0.5.0.
Date: 2026-08-10.

Round 5 and the four rounds before it are recorded in `docs/releases/v0.5.0-abort.md` and
`docs/releases/v0.4.0-abort.md`. Round 5 was the first five-of-five GO.

This round is a patch, and a patch is where a review is most tempted to rubber-stamp. It did not:
**Station 2 returned NO-GO on a defect this release introduced**, the defect was fixed, and the
station was re-run. That sequence is recorded below rather than smoothed away.

## A — Assume Failure (premortem, written before the verdicts)

It is three months on and this patch is the one people point at. The most likely reasons:

1. **The new dialog is worse than the silence it replaced.** A panic that Wails absorbed invisibly now
   raises a blocking native modal. If the panicking operation repeats, so does the modal.
2. **21 `defer` lines were inserted into `app.go` by a script.** If one landed anywhere but first, the
   code above it is unguarded and the gate would still pass if the gate checks presence, not position.
3. **The packaged app was not driven for this candidate.** This is the same premortem line as Round 5,
   and it is the line that found #53 after Round 5 shipped.
4. **The dialog instructs the user to restart, and the app has no menu bar** (#57), so `Cmd+Q` may have
   no provider. An instruction the user cannot perform is not a remedy. *(This premise was false — see
   the correction at Station 2. The premortem is left as written, because a premortem is a record of
   what was feared beforehand, not of what turned out to be true.)*
5. **A panic while `a.mu` is held** would leave the mutex locked, and Wails' recovery keeps the process
   alive, so the next caller blocks forever — a second silent hang stacked on the first.

**Four of five GO on the first pass, one NO-GO that produced a code change, five of five after it.**
The NO-GO is the finding of this round and is written up in full at Station 2.

### Station 1 — Competitor / Attacker

New surface introduced: a panic record carrying `operation`, `message` and `stack`, and a native
dialog carrying `operation`.

- The dialog interpolates **only** `operation`, which is a compile-time constant supplied by the guard
  at each call site. No attacker-controlled bytes reach it.
- `message` and `stack` reach the trail, where `eventlog` JSON-encodes every value — the existing
  design constraint that stops a document path containing a quote or newline from forging a record.

**Residual, and the reason this GO is qualified: panic recording is not capped, and the trail is
trimmed newest-first.** A document that reliably panics a bound method produces a record per attempt,
evicting the first panic and the context that preceded it — precisely inverting what root-causing
needs. This repo already solved the same shape for refused link schemes by capping per distinct href,
and the reasoning recorded there applies unchanged. Filed as
[#63](https://github.com/robot-accomplice/dr-markdown/issues/63). Not a blocker: it degrades a
diagnostic under a precondition that already means the app is broken, and before this release the
same scenario produced no record at all.

### Station 2 — Worst-Case Customer

**First pass: NO-GO.**

`UpdateContent` is pushed by the frontend debounced on every edit. A panic on that path repeats for as
long as the user types. `reportPanic` as written raised a **blocking** native dialog on every
occurrence, so a single broken document would put the app behind a modal storm the user cannot type
past.

That is strictly worse than the behaviour it replaced. The old behaviour was a silently dead call with
a usable app; the new one was a usable app made unusable by its own error reporting. A patch that
makes the failure louder must not make the product worse at the same time.

**Fix:** every panic is still recorded; the dialog is capped to one per session via `sync.Once`. One
per session rather than one per distinct operation, because the dialog's instruction is "restart", and
that does not improve on repetition. The cap is deliberately not guarded by `a.mu` — a panic raised
while `mu` is held would otherwise deadlock its own report. Pinned by
`TestRepeatedPanicsRecordEveryTimeButShowOneDialog`, which asserts three records and one dialog.

**Re-run: GO.**

Premortem item 4 stands but does not block: the dialog says restart, and with no menu bar `Cmd+Q` may
have no provider (#57). Quit remains reachable from the Dock icon's context menu, so the instruction
is performable, just not by the obvious route. Recorded here so that #57 is understood to have a
second consequence beyond the missing menu itself.

> **Correction, added 2026-08-10 after the release was published.** The paragraph above is wrong, and
> it is left in place rather than edited because an ABORT record is the account of a review as it was
> actually conducted. Driving the installed v0.5.1 DMG showed the app **does** have a menu bar —
> `Dr. Markdown`, `Edit`, `Window` — and the app menu contains **`Quit Dr. Markdown ⌘Q`**, which was
> used to quit it. AppKit supplies a default menu bar when an application sets none; the source facts
> the claim rested on were all true, and the conclusion was still false.
>
> **This does not change the verdict**, and it removes a concern rather than adding one: the restart
> instruction is performable by the obvious route after all. The station's actual finding — the modal
> storm — is unaffected.
>
> The review inherited this claim from the handover instead of checking it, which is the failure worth
> keeping: **a station that accepts a premise from a document has reviewed the document, not the
> product.** Every station here that returned a finding did so by reading source or driving something.
> The one place this review took a claim on trust is the one place it was wrong.

### Station 4 — Future Me (6 months)

Round 5 blocked-with-residual on: *"A reported frontend failure is now reproducible from recorded
state; a hard crash still is not."*

That residual is closed, and closing it corrected a belief the project had recorded as fact. `recover()`
appearing nowhere in this repo was a true grep and a false conclusion — the recovery lives in Wails,
which means the process always survived a bound-method panic. What it did instead was worse than
crashing: the dispatcher returns an empty result, `darwin/frontend.go` passes it to `Frontend.Callback`,
the runtime's `Callback` throws on `JSON.parse("")` before reaching the pending callback, and no call
timeout is ever armed. **The frontend's `await` never settled.**

A panic now carries operation, message, stack and build version into the trail, so a user's report can
be reconstructed. What replaces the old residual is narrower and both halves have issues: the call
still never settles ([#61](https://github.com/robot-accomplice/dr-markdown/issues/61)), and a panic
raised before the `App` and its log exist has nothing to write to
([#62](https://github.com/robot-accomplice/dr-markdown/issues/62)).

Premortem item 2 was checked and cleared: coverage is enforced by two source-parsing gates that assert
the guard is the **first statement**, not merely present. The first version of that detector matched 17
of 18 methods, because `UpdateContent` is written on one line — it reported a method clean by never
looking at it. It now counts signatures against bodies, so a skip fails loudly instead of passing
quietly.

**GO.**

### Station 5 — Domain / Data Integrity

Nothing in this release touches serialization, the fidelity registry, or the write path. The
reserialization class is carried forward unchanged and still accepted.

Premortem item 5 was checked rather than assumed. Five of the six `a.mu.Lock()` sites in `app.go` use an
explicit `Unlock()` rather than `defer`, so a panic between them would leave the mutex held — and
because Wails keeps the process alive, the next caller would block forever. Every one of those critical
sections was read: they contain field assignments, a slice append and two reads. None can panic in
practice. The hazard is real in shape and unreachable in this code, so it is recorded here rather than
filed.

The dialog's instruction is "copy your text out and restart" rather than "carry on", which is the
correct advice for a process whose state is no longer understood.

**GO.**

## O + R — Failure Review Board

### Ranked failure modes

1. A repeating panic evicts the trail that would explain it — #63, Station 1.
2. A panicking call never settles, so the frontend cannot report what the dialog does — #61.
3. A panic before the trail exists is still unrecorded — #62.
4. ~~The restart instruction is awkward to perform without a menu bar — #57, second consequence.~~
   **Withdrawn 2026-08-10:** the menu bar exists and `Cmd+Q` works. See the correction at Station 2.

### Root-cause cluster

Three of the four trace to the same place: **the app does not own its failure path.** Recovery,
callback delivery and the decision to keep running all live in Wails, and the app can only observe
them. That is now a roadmap item (`wails-exit-path`), scoped from the source: Wails is imported by two
files and all 11 native operations already sit behind `nativePort`.

### The one fix

Capping the dialog. It was the only finding that made the product worse than before the release, and it
was introduced by this release.

### Acceptable risks, each justified

- **#63, trail eviction** — degrades a diagnostic under a precondition that already means the app is
  broken; strictly better than the no-record status quo.
- **#61, unsettled promise** — closing it means either a dead process or changing every binding's
  timeout semantics; neither belongs in a patch whose purpose is visibility.
- **#62, pre-App panic** — needs a trail that does not depend on the `App`, which is a change to
  construction order, not a guard.
- **Reserialization class** — unchanged, disclosed, measured by two gates that fail in both directions.

### Dealbreaker

A dealbreaker would be any change to the write path, or a dialog that could not be dismissed. Neither
is present.

## T — Go/No-Go

### VERDICT: **GO**

Five of five, after one NO-GO that was fixed rather than argued down. The value of this round is that
the NO-GO came from the review and not from a user: the modal storm passed every automated gate,
because no gate asks whether a correct behaviour is a tolerable one.

**Conditions carried, not resolved:** #61, #62, #63 and #57 are open and named. The packaged app must
be installed and driven before publishing — that is what found #53 after the last release, and it is
the one premortem item no gate here covers.
