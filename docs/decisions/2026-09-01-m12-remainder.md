# M12 remainder: checksums, packaged smoke test, update-channel policy

Date: 2026-09-01
Status: approved design
Release item: `m12-packaging-signing-updates` in v1.7.0 (`docs/architext/data/releases/v1-7-0-desktop-integration-and-packaging.json`)
Issue: #11 (M12: Packaging, signing, updates, and platform hardening)

## Background

M12 shipped signing and notarization in v1.6.2/v1.6.3. Three acceptance
criteria from #11 remain:

1. Release artifacts include checksums.
2. A packaged-app smoke test passes before release publication. The host gates
   (`-menu`, `-close`, `-quit`, `-nav`, `-walk`, `-gates`) exist but run against
   a `go build` binary, not the packaged artifact, and only as a manual step.
3. An alpha/beta/stable update-channel policy — a decision before it is code.

## 1. Checksums

Checksums are produced at publish time over the final-named staged artifacts,
not in `build-macos.sh`. The build script's DMG is named `dr-markdown.dmg` and
the ceremony renames it per-arch; a build-time `.sha256` would reference the
wrong filename and duplicate the publish-time mechanism.

Changes to `docs/RELEASE.md`:

- Step 6 (Build and notarize) gains, after both DMGs are staged:

  ```sh
  cd <staging>
  shasum -a 256 dr-markdown-X.Y.Z-macos-arm64.dmg dr-markdown-X.Y.Z-macos-universal.dmg > SHA256SUMS.txt
  ```

- Step 7 (Publish) attaches `SHA256SUMS.txt` to `gh release create` alongside
  the two DMGs.

- Step 8 (Close out) gains a verify-what-users-get step:

  ```sh
  gh release download vX.Y.Z --dir <tmpdir>
  (cd <tmpdir> && shasum -a 256 -c SHA256SUMS.txt)
  ```

  The checksums must cover the exact bytes a user downloads, not only the ones
  staged locally.

## 2. Packaged smoke test — `tools/smoke-macos.sh`

A new script the release ceremony runs on both staged DMGs after step 6 and
before step 7 (publish). Any failure exits non-zero and aborts the release.

For each DMG argument:

1. Mount read-only (`hdiutil attach -nobrowse -readonly`).
2. Copy `Dr Markdown.app` to a `mktemp -d` directory.
3. Assert the bundle's `CFBundleShortVersionString` equals the repo's
   `VERSION` file.
4. Run the unattended in-binary gates against the **packaged** binary:
   `-menu`, `-close`, `-quit`, `-nav`, `-walk`, `-gates`. The dirty gates stay
   manual — they need a human to answer the save dialog.
5. Verify what a user's machine will conclude:
   `codesign --verify --deep --strict`, `xcrun stapler validate`,
   `spctl -a -vvv -t exec` on the app, and
   `spctl -a -vvv -t open --context context:primary-signature` on the DMG.
6. Clean up, in this order: unregister the temp copy and the mounted copy from
   LaunchServices (`lsregister -u`), remove the temp dir, detach the DMG.
   Measured 2026-09-01: mounting a DMG re-points `com.drmarkdown.app`
   resolution at the `/Volumes` copy, so the unregistration is load-bearing,
   not tidiness. Cleanup runs via trap on any exit.

**Ad-hoc builds fail by default.** Without a Developer ID signature the
Gatekeeper checks fail, and that is deliberate — the build script's rule is
that a request for a distributable artifact must never quietly produce an
undistributable one. An explicit `--ad-hoc-ok` flag skips the Gatekeeper checks
(steps 5 minus `codesign --verify`) for local iteration; the ceremony never
passes it.

Testing the script itself: run it with `--ad-hoc-ok` against a locally built
DMG, and in strict mode against the notarized v1.6.2 DMGs retained in
`build/` — that exercises the full Gatekeeper path without cutting a release.

RELEASE.md gains the invocation between steps 6 and 7:

```sh
tools/smoke-macos.sh <staging>/dr-markdown-X.Y.Z-macos-arm64.dmg \
                     <staging>/dr-markdown-X.Y.Z-macos-universal.dmg
```

## 3. Update-channel policy

Decided 2026-09-01: **stable + pre-release betas.**

- **stable** — a GitHub Release cut from `main` by the release ceremony. This
  is the only channel ordinary users ever see.
- **beta** — a GitHub pre-release (tagged `vX.Y.Z-beta.N`), published only
  when external soak is wanted. Same signing, notarization, checksum and
  smoke-test requirements as stable.
- **alpha** — local and CI builds. Never published.

No in-app updater exists, so channels are a publishing contract, not app
behavior. If an updater is ever adopted, this policy maps directly onto its
channels: the app would track stable, with beta opt-in.

Recorded in: a short "Channels" section in `docs/RELEASE.md`, this decision
record, and the Release Truth summary for `m12-packaging-signing-updates`.

## Out of scope

- Auto-update machinery (Sparkle or otherwise). The policy deliberately leaves
  room for it.
- The dirty close/quit gates, which remain manual by design.
- Any change to signing or notarization, which already ship.
