# Host replacement — decision and measurement

Date: 2026-08-10. Status: A and D rejected. B (own the host) measured and viable.

## The options, and the verdicts

### A — Wails v3: REJECTED

Not on capability. v3 meets all four stated requirements: bindings generated by static analysis,
`options.PanicHandler` with typed `CallError` rejection, a controllable native surface, and Windows
and Linux support. It is rejected on **the relationship**, for three maintainer reasons:

1. **No control over the internals of one of the biggest pieces of the application.**
2. **At the mercy of the dependencies available and the upstream bug-resolution schedule.** Not
   hypothetical — see #61 below.
3. **A rich target for upstream supply-chain attack.** v3's module graph carries **151 module
   lines**, including `modernc.org/sqlite`, two websocket implementations (`coder/websocket` and
   `gorilla/websocket`), `bubbletea`, `glamour`, `pterm`, `nfpm`, `zalando/go-keyring` and
   `wailsapp/task`. Most is CLI and build tooling rather than linked application code, but all of it
   is in the trust surface of the module the application depends on.

**#61 confirmed present at `v2.14.0`**, which shipped 2026-08-10 and fixed only a WebView2
bootstrapper crash. Verified in the caller rather than inferred from the dispatcher — the shape of
error this project has made three times. `dispatcher.ProcessMessage` *does* convert the panic to an
error:

```go
if e := recover(); e != nil { err = fmt.Errorf("%v", e) }
```

but `internal/frontend/desktop/darwin/frontend.go` then does:

```go
result, err := f.dispatcher.ProcessMessage(message, f)
if err != nil {
    f.logger.Error("%s", err.Error())
    f.Callback(result)   // result is ""
    return
}
```

The empty string reaches `Frontend.Callback`, the runtime throws on `JSON.parse("")` before the
pending callback, and no call timeout is ever armed. **The promise never settles.** True premise,
and the conclusion only holds because the caller was read.

### A fourth objection, CHECKED AND REFUTED

That the framework involves TCP between Go and the frontend. **It does not**, in v2 or v3. Recorded
so it is not derived a third time.

`net.Listen` appears in exactly two files under `v3/pkg`, both excluded from a normal desktop build:

```go
// v3/pkg/application/application_server.go
//go:build server

// v3/pkg/application/mcp_enabled.go
//go:build mcp && !ios && !android
```

`websocket_server.go` is `//go:build server` too. v3's default transport is an HTTP-shaped handler
chain over a custom URL-scheme handler, served in-process. **HTTP shape, no HTTP socket.** The
equivalent v2 finding (no `net.Listen`, `http.Serve` or `ListenAndServe` in `internal/` outside
tests; `wails://` served by a `WKURLSchemeHandler`) was re-confirmed by grep against
`v2@v2.13.0` in the module cache.

### C — macOS-native now: NOT A SEPARATE OPTION

The original spec scored C as failing the "Windows and Linux artifacts" requirement by design. That
was wrong. **Windows and Linux are unbuilt today** — only `tools/build-macos.sh` exists, and CI
produces no artifact for either. A macOS-first host defers nothing that currently exists. C is B,
staged.

### D — direct rendering, no webview: REJECTED

Its main argument was that it closed the re-serialization class. That class closed **with the webview
in place** on the same day — see `2026-08-08-markdown-fidelity-scope.md`, probe result 2026-08-10. D
remains blocked on foundations that do not exist: no mature Go rich-text editing engine, and no
viable native Mermaid renderer.

### B — own the host: MEASURED AND VIABLE

See below.

## The measurement

A working macOS host, no framework, first-party frameworks only:

| file | lines |
| --- | --- |
| `host_darwin.go` | 233 |
| `host_darwin.m` | 223 |
| `spike_main_darwin.go` | 30 |
| **total** | **486** |

Against **241** — the boundary it replaces (`host.go` 45, `host_wails.go` 171, `main.go` 25) — and
against Wails' **5,116**-line macOS layer.

**486 includes its own test harness**, and that should not be quietly counted as host code: the
self-running gate script, the console-error capture, the boot diagnostics and the asset logging are
measurement scaffolding, not product. The host proper is meaningfully smaller. It also does **not**
include the twelve `nativePort` operations, which are unbuilt.

The honest reading: **the same order of magnitude as the boundary it replaces, not as the framework
it replaces.** The 5,116 figure was never the relevant comparison — it buys a system tray, custom
window chrome, drag regions, a frameless-window implementation and a dev server this application
does not use.

## The gates

All four pass. Run by the binary itself and printed to stdout, not read out of a Web Inspector by
hand — a measurement that depends on a person typing four expressions correctly is one nobody
repeats.

```
GATES:
{
  "diag_app_exists": "object",
  "diag_errors": [],
  "gate1_app_ready": true,
  "gate2_ping": "pong:[\"hello\"]",
  "gate3_boom": "REJECTED: panic in Boom: deliberate panic from a bound method",
  "gate3b_survived": "pong:[\"still here\"]"
}
VERDICT: PASS
```

- **Gate 1 — the real frontend boots.** The entire shipped frontend, over a `drmd://` scheme handler
  serving `embed.FS`: `app.js`, `bridge.js`, the six markdown modules, the six fidelity modules, the
  2.8 MB Crepe bundle and the 2.6 MB Mermaid bundle. `window.__app.ready === true`.
- **Gate 2 — a bound call round-trips**, in the exact `globalThis.go.main.App` shape `bridge.js`
  resolves, so the existing frontend runs unchanged.
- **Gate 3 — a panicking bound call REJECTS.** This is #61, fixed, in a host we own. Under Wails the
  same call hangs forever.
- **Gate 3b — the dispatcher survived the panic** and still answers.

**The CSP concern was unfounded** and should not be raised again. `index.html` sets every directive
to `'self'`, and it works against `drmd://app` — as it already does against Wails' `wails://`, which
is registered through the identical `setURLSchemeHandler:forURLScheme:` call.

## What fought back — and this is the important part

### 1. A partial host cannot exist. Incremental replacement was never viable.

`frontend/dist/src/bridge.js` has **two** degradation styles, and only one is safe:

```js
setDirty: (d) => wails()?.SetDirty(d),                              // throws
openRecentDocument: (path) => wails()?.OpenRecentDocument?.(path),  // safe
```

The `?.` guards `wails()` returning **null**. Once `go.main.App` exists but lacks a method,
`wails()?.SetDirty(d)` is a `TypeError`. A deliberately minimal two-method host therefore boots the
whole frontend and then dies at `SetDirty` — and `boot()` catches that into `console.error`, so the
window renders the static shell from `index.html` and *looks fine*.

**Consequence, and it settles a sequencing question rather than being a nit: the host is
all-or-nothing.** There is no "second adapter alongside Wails, switched when it is ready" — the
frontend does not tolerate a host that implements a subset. Any replacement implements all eighteen
bound methods or the app does not boot. The spike passes Gate 1 only after wiring the full name list
with Go returning zero values.

Two of those zero values are **not** interchangeable with `null`: `FrontendReady` and
`ListFontFamilies` must return `[]`, because the boot path iterates what they return.

Whether to fix `bridge.js` to degrade uniformly is a separate decision. It is not a prerequisite for
B — it is a prerequisite for *staging* B.

### 2. cgo cannot hold Objective-C definitions

The first build failed to link with four duplicate symbols. **cgo emits the preamble into both its
main generated C file and `_cgo_export.c`**, so an `@implementation` in a preamble is compiled twice.
Declarations may live in the preamble; definitions must live in a `.m` file. The `.m`/`.go` split is
forced by the toolchain, not chosen for style.

What genuinely requires the Objective-C *language* is protocol conformance — AppKit and WebKit expose
no C API, and serving assets and receiving calls each need a conforming class. Wails' `WailsContext`
conforms to four protocols; this host needs two.

### 3. The boot failure was invisible to every standard instrument

`window.addEventListener('error')` and `unhandledrejection` both saw nothing, because `boot()`
catches its own failure into `console.error`. Only patching `console.error` at document-start
surfaced it. This is the project's own recorded lesson — a `ReferenceError` once hid behind
`console.warn` for two rounds of debugging — and it cost two more rounds here.

## What this does NOT establish

- **The twelve `nativePort` operations are unbuilt and unmeasured.** Dialogs, reveal, title, external
  URL. Low-risk AppKit wrappers, but their cost is real and is not in the 486.
- **Windows and Linux are untouched.** WebView2 is COM interop and is where the cost is. **A macOS
  result must not be read as a cross-platform one.**
- **Menus, drag-and-drop, file associations, packaging and signing** are not built.
- **Verification was manual and is not in CI.** The spike is excluded from the default build by
  `//go:build darwin && ownhost`; CI runs on Linux and compiles none of it. Acceptable because the
  spike ships nothing — not a pattern to carry into shipped code.
- **The panic path is proven for one deliberate panic**, not for the full failure surface.

## Recommendation

**Proceed with B, macOS first.** The measurement supports it: the host is the size of the boundary,
not the size of the framework, and it already does the one thing the framework cannot be made to do.

Sequencing follows from the `bridge.js` finding rather than from preference: **one cutover, not a
migration.** Build all twelve `nativePort` operations against the real AppKit APIs, keep
`host_wails.go` as the shipping host until they are done, and switch once. `TestOnlyTheHostFilesNameWails`
already guarantees nothing above the boundary has to change.

## Reproducing

Branch `probe/own-the-host`. No PR — the branch is the record.

```sh
go build -tags ownhost -o /tmp/drmd-spike . && /tmp/drmd-spike
```

Prints the gate verdicts and exits 0 on PASS. Full local gate green with the spike present:
`gofmt -l . && go vet ./... && ./tools/verify-vendor.sh && go test ./... -count=1`.

## Release constraint — maintainer decision, 2026-08-10

**No further release ships until every vestige of Wails is eliminated.**

This is a release gate, not a preference, and it changes what the work is. The host replacement is no
longer an improvement competing with other roadmap items; it is the only path to a release. The
unreleased code-block-chrome fix on `develop` (PR #67) does not ship as a point release ahead of it.

It also promotes a question the spike did not answer. **The 486 lines measure the runtime host. They
measure nothing about packaging**, and packaging is what actually stands between this project and a
release.

## Elimination inventory

Taken from the source on `develop`, so "all vestiges" is a checklist rather than a phrase.

### 1. The host — measured, 486 lines

| what | action |
| --- | --- |
| `host_wails.go` (171 lines) | delete; replaced by `host_darwin.go` + `host_darwin.m` |
| `main.go:9` — `host := wailsHost{}` | becomes `darwinHost{}` |
| `go.mod` | drop `github.com/wailsapp/wails/v2`, and the indirects `wailsapp/go-webview2` and `wailsapp/mimetype` |

### 2. Packaging — THE SHIP BLOCKER, and it is unmeasured

`tools/build-macos.sh:30` is the whole of it:

```sh
wails build -clean -platform "$PLATFORM"
```

That single command performs app-bundle assembly, `Info.plist` templating, icon embedding and DMG
creation. `build/darwin/Info.dev.plist` is its template. **None of this is in the 486 lines, and none
of it was in the spike's scope.**

Under the release constraint above, this is the largest unmeasured item on the critical path. It
should be sized the same way the host was — by building the irreducible core and measuring it —
before any estimate is offered.

### 3. Version identity — a trap, and it must be handled BEFORE deletion

`app_version_test.go:17` reads `wails.json` and compares `info.productVersion` against `appVersion`.
Release mechanics require both to be bumped together, and that gate is what catches drift.

Deleting `wails.json` deletes **both the version source of truth and the control that protects it**.
A replacement source must exist and be pinned by an equivalent test before `wails.json` is removed —
otherwise the first post-Wails release ships with an unverified version, which is precisely the class
of defect the event trail exists to make diagnosable.

### 4. The JavaScript contract

- `frontend/dist/src/bridge.js` — the `wails()` helper, the `globalThis.go.main.App` shape it
  resolves, and the "not running under Wails?" warning text.
- `bridge_contract_test.go:41` — its detector regex matches `wails()` by name.

**The shape itself is worth keeping, at least at first.** `globalThis.go.main.App` is what the spike
implemented and it let the entire frontend run unchanged. Renaming it is a separate, optional change
that should not be bundled with the host swap — one risky change at a time.

Also fixed here: the partial-host degradation defect recorded above. Entries written
`wails()?.Method(x)` rather than `wails()?.Method?.(x)` throw once the object exists without the
method.

### 5. Tests and gates

- `host_boundary_test.go` — `hostFiles` and the split `"wailsapp" + "/wails"` needle. Once no
  framework is imported, this gate stops meaning anything and must be re-aimed at whatever the new
  boundary is, or retired deliberately rather than left passing vacuously.

### 6. Documentation and Architext

`README.md` plus nine files under `docs/architext/data/`. Note that node **ids** carry the name —
`wails-desktop-app`, `wails-go-api`, `wails-bridge` — and are cross-referenced from `views.json` and
`flows.json`, and `decisions.json` holds `local-wails-app`. Renaming ids is a coordinated edit that
validation will catch if done partially; it is not a find-and-replace.

## Revised recommendation on sequencing

The `bridge.js` finding already established that the host is **one cutover, not a migration**. The
release constraint adds a second ordering fact: **packaging is on the critical path and the host is
not sufficient.**

So the order is:

1. **Size the packaging replacement.** A spike, same discipline: build a `.app` bundle and a DMG
   without `wails build`, verify with `lipo -archs` and `PlistBuddy`, and measure it. Until this
   number exists, no date should be offered for a post-Wails release.
2. **Move version identity** off `wails.json` to a source that survives, with a drift gate proven
   able to fail.
3. **Build the twelve `nativePort` operations** against real AppKit.
4. **Cut over in one commit**, delete `host_wails.go`, drop the `go.mod` entries.
5. **Re-aim or retire** `host_boundary_test.go`; update Architext ids and README.

Steps 1 and 2 are the ones that can be done now and are not blocked on anything.
